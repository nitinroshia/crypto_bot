# Work order 1.4: pair expansion — ETH/USDT and BTC/USDT

Issued by the mathematician, 2026-09-23. Owner-approved decision, not a proposal.

## 1. Decision and rationale

ETH/FDUSD is retired as an execution-pair candidate. Its liquidity — 2.0-4.5% of ETH/USDT's daily
trade count in every fully-covered 2026 month (the one partial month, January, isn't comparable) —
makes it unsuitable for execution regardless of any research finding, since realized slippage on a
market that thin would likely run well above the 0.02-0.03% planning assumption in the cost model.

ETH/USDT becomes the execution pair. BTC/USDT — used until now only as a same-sign replication check
for S1 and S2 — is elevated to a full second research and execution pair, run through the complete
pipeline in its own right, not just checked for sign agreement.

ETH/FDUSD's existing results (the fingerprint, the dead lead-lag result, the Task 2 baseline) stay as
historical reference. No further formula work targets ETH/FDUSD. Its data stays on disk and its
liquidity monitor can still be run cheaply if ever useful, but nothing in the active queue depends on
it.

## 2. What changes in the pipeline

Every pre-registered task (S1, S2, Task 3, and Task 4 once relevant) now runs on ETH/USDT AND
BTC/USDT as two separate families, each independently gated: its own Holm adjustment, its own
registry entries, its own freeze and its own one-shot forward test. Nothing about a pair's own
pipeline changes — Holm, walk-forward mechanics, the economic gate, the three-way classification, the
non-stationarity/by-year rule, and end-of-segment handling all apply per pair exactly as already
specified.

"Replicate the sign on BTC, report only" (the old S1/S2 language) is retired. BTC/USDT gets the full
pipeline. In its place: when either pair's candidate freezes, report the OTHER pair's same-cell point
estimate, sign, and discovery p-value (if it has run) as a labeled context column. This is
informative, not gating — a candidate is not required to replicate cross-pair to be promoted. The two
assets need not share the same effect, and requiring transfer would risk killing a genuinely
asset-specific finding.

Registry naming: family names become pair-qualified so no report can be ambiguous about which pair a
result belongs to, e.g. `S1-ETHUSDT`, `S1-BTCUSDT`, `S2-ETHUSDT`, `S2-BTCUSDT`, `Task3-ETHUSDT`,
`Task3-BTCUSDT`. Since item 2 (the registry, guard, and holdout lock) is still being built, add the
pair-qualified naming to its schema now rather than retrofitting it later.

## 3. Sample design: same cutoff for both pairs

BTC/USDT discovery and holdout use the identical cutoff as ETH/USDT: 2025-08-31 23:59:59 UTC
inclusive, walk-forward fit 365 days / validate 90 days. Same reasons as before (comparability), plus
one specific to adding a second pair: ETH and BTC returns are correlated, so using different cutoffs
would risk one pair's holdout period doing work inside the other pair's discovery period. Same cutoff
for both removes that risk entirely. Every cutoff-mechanics rule already specified (origin purge,
entry-time convention, holdout exposure and descriptive-vs-hypothesis-specific reads) applies
identically to BTC/USDT.

## 4. Data needed (one owner run)

1. BTC/USDT 5m and 15m, same span as ETH/USDT's 5m store (back to 2017-08-17 04:00; build 15m with
   the traded-minutes resample rule). BTC/USDT currently has only 1h and 1d — Task 3 needs 5m/15m and
   doesn't have it yet for this pair.
2. Run the same gap check already done for ETH/USDT's 1h (the 128-missing-hours finding) on
   BTC/USDT's new 5m/15m data: report row counts and any missing bars, masked not dropped, same
   methodology.
3. Report annualized realized volatility (from daily log returns, close-to-close) for ETH/USDT and
   BTC/USDT separately, computed ONLY over the discovery sample (<= 2025-08-31 — this is a
   descriptive statistic restricted to discovery data, not a violation of the holdout rule). I want
   this to check whether section 3's break-even hit-rate table needs a pair-specific version. The
   materiality threshold M (0.35% gross per round trip) does NOT need this — it's cost-derived, not
   volatility-derived, and stays identical for both pairs regardless of what the volatility comparison
   shows.

## 5. Order of work

No change to the existing priority (S2 and S1 first, then Task 3). Run both pairs' versions of a
given task together rather than staggering them — it's the same formula pointed at different data, so
there's no reason to sequence them separately. Item 2 continues as already scoped; fold in the
pair-qualified registry naming (section 2) as you build it, not after.

## 6. Documentation

Update `project_context.md` (and `context/STATUS.md` at the next status refresh) to state plainly:
ETH/USDT and BTC/USDT are the project's two live pairs, for both research and execution. ETH/FDUSD is
historical reference only.
